# ADR-0004: 플래너 구조화 출력

- 상태: 채택 (2026-10-19), **Phase 1.5 스파이크로 측정 후 갱신 (2026-10-20)**
- 근거: TRD 7.1, 10절, 계획 Phase 1.5

## 결정

1. QueryPlan 은 JSON 스키마 구조화 출력 → Pydantic 검증 → 실패 시 오류를 붙여 1회 재시도로 얻는다.
   검증(실재·연산자·값·권한·참조 값)에 걸리면 오류를 붙여 1회 재계획한다.
2. 플래너 출력에는 `query` / `not_query` 외에 **`cannot_answer`** 가 있다. 조건을 스키마로 표현할 수
   없으면 조건을 빼지 말고 이것을 낸다 → `failed(plan_invalid)`.
3. 운영 기본 모델(planner·answerer): **`gemma4:e4b`** (`config/llm.yaml`).

## 무엇이 정답률을 올렸나 — 모델이 아니라 파이프라인 결함이었다

기준선 오답의 대부분은 **모델이 맞게 답했는데 우리 쪽이 버린** 것이었다. 같은 모델에서 4/12 → 12/12 가 됐다.

| 결함 | 증상 | 고친 것 |
|---|---|---|
| 문장 나누기가 `입니다. [[인용]]` 의 인용을 다음 '문장'으로 떼어 냈다 | 모든 인용이 빈 문장에 붙어 `value_mismatch` — 맞는 답이 ③ | 인용만 있는 조각·앞머리 인용은 앞 문장에 붙인다 |
| 데이터 블록이 `value (평균(위험등급)): 2.56` 형식이었다 | 모델이 라벨을 인용에 베꼈고(`[[q:1#value (건수(건))]]`) **깨진 인용은 기록 없이 지워졌다** | 줄마다 `인용키 \| 이름 \| 값`, 깨진 인용은 `malformed` 로 기록 |
| 평균을 긴 소수(2.5555…)로 줬다 | 모델이 반올림 → 정확 일치 대조 실패 | 서버가 소수 둘째 자리로 반올림 |
| 프롬프트 예시 셋 중 둘이 count 였다 | 목록 질문에 count 를 붙였다(q02·q06·q07) | 목록 예시 추가, "aggregate 는 개수·합계·평균을 물을 때만" |
| 조건 되풀이 문장("2015년 이전에 설치된 철탑은 다음과 같습니다")이 사실 문장으로 잡혔다 | 맞는 목록 답이 ②(추정) | 조건 값을 걷어 낸 뒤 사실 여부를 본다(TRD 8.2-2 v0.5) |

## 조용히 틀리는 경로 둘 — 발견하고 막았다

1. **코드 속성에 이름을 넣었다.** "서울 지역 시설" → `region_code = '서울'`. 형식상 멀쩡하고 실행도
   성공해 0건 → "조건에 맞는 객체가 없습니다". 사용자는 서울에 시설이 없다고 믿는다.
   → **참조 값 실재 대조**(`query/references.py`): 링크 FK 속성의 `eq`·`in` 값이 대상 타입 pk 로
   있는지 확인하고, 없으면 재계획.
2. **조건을 뺐다.** 같은 질문에 gpt-oss:20b 는 지역 조건을 통째로 빼고 전 지역 시설 20건을 답했다.
   조회 조건 문장("시설 · 최대 20건")만이 단서였다.
   → **`cannot_answer`** 출구 + 프롬프트 규칙("표현할 수 없는 조건을 빼지 말 것"). 최종 실행에서
   네 모델 모두 `failed(plan_invalid)` 로 정직하게 밝혔다.

⚠ 2번은 **결정론적으로 막을 수 없다** — 질문에 있던 조건이 계획에서 빠졌는지 판정하려면 질문을
해석해야 하고, 그것은 유사도 판정이 된다. 지금의 방어는 프롬프트와 화면의 조회 조건 문장뿐이다.
평가 게이트(Phase 7)에 '조건을 빼면 오답이 되는' 문항을 계속 늘려 회귀를 잡는다.

## 모델 선택 근거

- 정확도가 같은 넷 중 **지연이 압도적으로 짧다**(p50 1.3초 — gpt-oss:20b 의 1/11).
- 추정 비율이 낮다(3.2%). gemma4:12b 는 16.7%로, 인용을 덜 단다.
- 구조화 출력 JSON 실패는 **전 모델 0건** — 이 크기 스키마에서는 형식 실패보다 **의미 실패**(잘못된
  연산자·조건 누락)가 문제다. 그래서 재시도 예산(1회)은 충분하고, 검증 오류를 붙인 재계획이 효과가 있었다.

## 한계와 재검토 조건

- **표본이 12문항이다.** 실제 도메인 팩이 정해지면 문항을 늘려 다시 잰다(평가 게이트, Phase 7).
- ~~탐색(traverse)·대화 맥락은 아직 없다~~ → Phase 4 에서 다시 쟀다(아래 절).
- 목록 머리말의 "5개"(limit)는 근거가 없어 ②가 된다. 결과 건수를 인용 가능한 근거로 주면 해소된다
  — 후속 개선.
- qwen3:8b 의 긴 답변 지연(10행 90초)은 원인을 보지 않았다(선택 대상이 아니어서).
- **재검토 조건**: 골든 문항 확장 후 정답률이 게이트 미만이거나 `plan_invalid` 비율이 오르면 모델을
  올린다(gemma4:12b → gpt-oss:20b 순). 모델 교체는 평가 게이트 통과가 조건이다(TRD 10절).

### 조건 누락 — 일부를 결정론적으로 잡게 됐다

위 "결정론적으로 막을 수 없다"는 여전히 일반적으로 참이다. 다만 한 갈래는 잡는다: **질문에 나온 숫자가
계획(조건 값·limit·맥락 식별자) 어디에도 없으면** 검증 오류로 재계획시키고, 그래도 없으면
`plan_invalid` 로 밝힌다(`query/coverage.py`, 숫자 포함·수 값 같음만 — 유사도 없음). enum 낱말은
"변전소별 개수"처럼 조건이 아닌 쓰임이 흔해 보지 않는다. 답변 프롬프트에도 "레코드를 스스로 다시
거르지 말고, 조회 조건에 없는 질문 조건은 반영되지 않았다고 말하라"를 넣었다 — 조건 누락을 답변
모델이 감추지 못하게.

재현: `scripts/seed_domain_pack.py --pack sample` → `scripts/spike_plan.py --models gemma4:e4b …`

## Phase 11 보강 — 채팅에서 Action (2026-10-20)

플래너 출력에 `kind: action` 과 `ActionProposal{action_type, target, params[{name, value}]}` 를 더했다
(TRD 17.3). 프롬프트의 Action 규칙·예시는 **요약에 요청할 수 있는 Action 이 있을 때만** 붙인다 — Action 이
없는 배포의 프롬프트는 위에서 잰 그대로다. 예시는 샘플 팩과 다른 가상의 Action(`escalate_ticket`·
`close_ticket`)으로 들고, 값이 없는 요청("우선순위 바꿔줘" → `params: []`)의 예시를 꼭 넣었다 — 없으면
모델이 값을 지어낼 자리가 생긴다. 예시 키 순서는 `PlannerOutput`·`ActionProposal`·`ActionParamValue`
필드 순서와 같다(단위 테스트로 고정).

샘플 팩에 Action 2개(`adjust_risk_grade`·`request_inspection`)와 골든 Action 문항 7개(식별자·이름·enum·
맥락 대상 4개, 막아야 할 것 3개 — 없는 식별자·없는 이름·질문에 없는 값)를 더해 gemma4:e4b 로 쟀다.

| 측정 | 전체 정답 | Action 정답 | 지어내기 | 첫 계획 무효 | 최종 plan_invalid | p50 | 근거 |
|---|---|---|---|---|---|---|---|
| spike(장애·권한 문항 제외 25문항) | 24/25 | **7/7** | 0 | 3 | 1 | 1.3초 | `data/0004-spike-20261020T131706Z.json` |
| 평가 게이트(record, 32문항) | 정답률 1.0 | 파라미터 정확도 1.0 | 0 | — | — | p95 10.4초 | `domain-packs/sample/llm_cassette.json` |

- 틀린 1건은 `u01`(스키마에 없는 속성을 묻는 문항)이 `ok/③` 로 나간 것으로, Phase 7 녹화 때와 같다(③ 은 본문을
  보이지 않아 불변식 위반이 아니다). 기존 조회 문항의 회귀는 없었다.
- 첫 계획 무효 3건은 막아야 할 Action 문항(a05·a06·a07)이다 — 대조 오류를 붙여 재계획해도 대상·값이 질문에
  없으므로 `ready=false` 로 남는 것이 정답이다. 모델은 없는 대상을 다른 실재 시설로 바꿔 끼우지 않았고,
  빠진 위험등급 값을 지어내지 않았다.
- 모델이 지어내더라도 막히는 것은 모델이 아니라 서버 대조다(`actions.params`): 대상을 가리키는 말이 질문에

## Phase 12 보강 — Function (2026-10-30)

요약에 Function 이 있을 때만 프롬프트에 `FUNCTION_RULES` 를 붙이고 구조화 출력 스키마를 `FunctionPlannerOutput`
(`kind: function`, `FunctionCall{name, args[{name, value}]}`)으로 바꾼다(TRD 17.4). Function 이 없는 배포는
스키마(`PlannerOutput`)와 프롬프트 모두 위에서 잰 그대로다 — 단위 테스트가 스키마 모양을 고정한다. 예시는 가상의
Function(`close_rate`·`team_backlog`)으로 들고, 인자 없이 부르는 예시와 **인자로 받을 수 없는 조건이 있어 부르지
않는**(`cannot_answer`) 예시를 넣었다. 예시 키 순서는 스키마 필드 순서와 같다(단위 테스트).

샘플 팩에 Function 2개(`high_risk_ratio` — 시설 유형별, 선택 인자 기준 위험등급 기본 4 / `region_high_risk_ratio`
— 지역명 필수, 내부 조회가 링크 탐색)와 골든 4문항(기본값·인자·탐색, 권한 1)을 더해 gemma4:e4b 로 쟀다.

  비율은?")가 ①로 나갔다. 지역 Function 은 요약에 없으니 플래너가 시설 유형별 Function 을 부르면서 질문에 없는
  기본값 `min_grade: 4` 를 채워 넣었고, 답변은 "대구 지역의 고위험 시설 비율은 …"이라며 전국 유형별 값을 늘어놓았다
  (지역 조건 누락). 프롬프트 규칙("인자로 받을 수 없는 조건이 있으면 부르지 않는다")과 예시만으로는 바뀌지
  않았다(플래너 단독 재기 2/2 같음). 그래서 **넣은 인자 값은 질문에 그대로 있어야 한다**는 결정론적 대조를 더했다
  (Action 값 파라미터와 같은 규칙, enum·bool 제외). 오류 문구에 "받을 수 없는 조건이 있으면 cannot_answer" 를
  함께 실어 1회 재계획하면 `failed(plan_invalid)` 가 됐다 — 게이트 통과.
- 반대 방향(질문의 숫자가 인자에 없음)은 기존 `query.coverage` 를 인자·내부 조건 값으로 넓혀 쓴다 — "위험등급 3
  이상을 고위험으로 볼 때"가 기본값 4 로 불리면 재계획된다.
- 이전 Phase 의 틀린 1건(`u01`, 스키마에 없는 속성)도 이번엔 `plan_invalid` 로 맞았다. 기존 조회·Action 문항의
  회귀는 없었다.
- 한계: Function 인자로 받지 않는 조건 중 **숫자도 인자 값도 아닌 것**(지역 이름 등)을 플래너가 빼고 부르면서 인자를
  하나도 넣지 않으면 결정론적으로 잡지 못한다(조회 계획의 조건 누락과 같은 한계, 골든 `required_conditions` 로
  감시). 조건 문장에 Function 이름·인자가 그대로 보여 사용자가 해석을 확인할 수 있다.
