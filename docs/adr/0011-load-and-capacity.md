# ADR-0011: 부하 측정과 용량 — DB 연결 풀 20+10, 동시 사용자 가안

- 상태: 채택(풀 설정) · 제안(PRD 7절 수치 — 사용자 확정 필요) (2026-10-20, Phase 8)
- 근거: TRD 13.2(동시 사용자)·15절(성능), 데이터 `docs/adr/data/load-phase8.json`, `load-phase8-pool30.json`

## 측정 방법

`scripts/load_test.py` — 가상 사용자마다 따로 로그인하고, 골든셋의 정상 단일 질문 12개(맥락·장애 주입·평가 역할 없는
`ok` 문항)를 사용자마다 다른 순서로 8개씩 보낸다. 지연 = 요청부터 SSE `done` 까지. 첫 이벤트(`stage`)까지도 잰다.

장비: 개발 PC 1대(api 1 프로세스 + PostgreSQL 18 + Neo4j 5.26 + Ollama, GPU 1장에 `gemma4:e4b` 가 전부 올라감).
샘플 팩(합성 30여 객체) — 데이터 규모가 작아 조회 비용은 무시할 만하고 지연은 거의 LLM 이다.

## 결과

| 동시 사용자 | 풀 | 요청 | 실패 | p50 | p95 | 최대 | 첫 이벤트 p95 | 처리량(건/분) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 5+10 | 8 | 0 | 1.6초 | 10.5초 | 10.5초 | 0.29초 | 19.1 |
| 4 | 5+10 | 32 | 0 | 2.5초 | 21.8초 | 27.0초 | 0.29초 | 23.6 |
| 8 | 5+10 | 64 | 0 | 5.6초 | 23.0초 | 29.1초 | 0.29초 | 29.7 |
| 16 | 5+10 | 128 | 0 | 16.7초 | 28.7초 | 33.4초 | **3.7초** | 44.6 |
| 16 | 20+10 | 128 | 0 | 18.2초 | 30.9초 | 34.7초 | 0.29초 | 40.3 |
| 24 | 20+10 | 192 | 0 | 25.5초 | 37.6초 | 42.2초 | 0.29초 | 42.3 |

- **결함(수정)**: 채팅 한 건은 답이 끝날 때까지(LLM 호출 포함) DB 연결 하나를 쥔다(`api/chat.py` 의 `session_scope`
  가 파이프라인 전체를 감싼다). 기본 풀 5+10 = 15 에서 16명째부터 연결을 기다려 첫 이벤트가 3~6초 늦었다. 풀을
  설정으로 내고(`ONTOBOT_DB_POOL_SIZE`·`ONTOBOT_DB_MAX_OVERFLOW`) 기본값을 20+10 으로 올렸다 → 16·24명 모두 0.29초.
  풀이 다 차면 `pool_timeout`(30초) 뒤 요청이 실패한다 — 동시 채팅 상한 = 풀 크기다.
- 처리량은 동시 16명 부근에서 분당 40여 건으로 **포화**한다(LLM 이 병목). 그 뒤로는 사용자가 늘수록 지연만 선형으로
  는다. 실패는 24명까지 0 — 실패보다 지연이 먼저 는다.
- 1명 p95 10.5초는 목록 질문(변전소 목록 등)의 답변 생성이 길어서다(단건·집계는 1~3초).
- 16명(20+10) 측정의 일부는 통합 테스트와 겹쳐 돌았다(DB 부하 소량). 처리량 차이(44.6 → 40.3)는 그 영향일 수 있다.

## 결정

1. DB 연결 풀 기본값 20+10(프로세스당). api 1 + worker 1 이면 최대 60 연결 — PostgreSQL 기본 `max_connections`
   100 안이다. api 를 늘리거나 사용자가 30명을 넘으면 풀과 `max_connections` 를 함께 올린다.
2. 파이프라인이 LLM 을 기다리는 동안 연결을 놓게 바꾸는 것(세션을 단계별로 나누기)은 하지 않는다 — 계획·실행·기록이
   한 세션이라는 가정이 트레이스·권한 판정에 걸쳐 있다. 연결 수가 실제 제약이 되면 다시 본다.

## PRD 7절 수치 제안 (확정은 사용자)

이 장비 기준(GPU 1장, gemma4:e4b). 운영 장비가 정해지면 같은 스크립트로 다시 잰다.

| 지표 | 제안 | 근거 |
| --- | --- | --- |
| P95 응답 시간 | **동시 8명에서 25초 이하** (1명 기준 12초 이하) | 8명 p95 23.0초, 1명 10.5초 |
| 동시 사용자 | **8명**(목표), 16명까지 실패 없이 수용 | 16명부터 처리량 포화, p95 30초 초과 |
| 조회 실패율 | 부하에서 0% (측정 552건 실패 0) | 위 표 |

평가 게이트의 `p95_ms`(가안, `evaluation/gate.yaml`)는 단일 사용자 순차 실행 값이라 이 표와 다른 축이다 — 부하
수치는 게이트에 넣지 않는다(CI 에 GPU 가 없다).

## 재검토 조건

운영 장비·모델이 바뀌면 다시 잰다. 실제 도메인 데이터(객체 수 수만 이상)에서는 조회 지연이 늘 수 있으므로 같은 측정을
그 데이터로 반복한다.
