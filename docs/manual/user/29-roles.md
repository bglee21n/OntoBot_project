# 29장 역할별 권한표와 점검표

## 29.1 역할 다섯 가지

| 역할(화면 표시) | 이름 | 하는 일 |
| --- | --- | --- |
| `user` | 챗봇 사용자 | 질문하기, 데이터 변경 요청 |
| `modeler` | 모델러 | 데이터 설계도(온톨로지)·데이터 소스·Action 정의 관리, 편집 충돌 처리 |
| `bot_builder` | 챗봇 빌더 | 골든셋(시험 질문)과 평가 |
| `domain_expert` | 현업 전문가 | 인터뷰 워크숍에서 업무 설명 |
| `admin` | 관리자 | 사용자·역할·읽기 권한·감사 로그·트레이스 관리, 그래프 대사·재구축 |

한 사람이 여러 역할을 함께 가질 수 있습니다(예: `modeler, user`). 역할은 관리자가 정합니다(「21장」).

> **주의** 역할과 별도로 **역할별 읽기 권한**이 있습니다. 어떤 역할이든 읽기 권한에 고른 객체 타입(시설·조직
> 등)만 채팅으로 조회할 수 있습니다. 관리자 역할도 읽기 권한을 받지 않으면 데이터를 읽지 못합니다.

## 29.2 메뉴별로 누가 무엇을 할 수 있나

표에서 ○는 할 수 있음, 보기는 화면을 볼 수만 있음, × 는 할 수 없음입니다.

| 화면·기능 | user | domain_expert | modeler | bot_builder | admin |
| --- | --- | --- | --- | --- | --- |
| 채팅으로 질문 | ○(읽기 권한 범위) | ○(읽기 권한 범위) | ○ | ○ | ○ |
| 대화 목록·다시 보기 | ○(내 대화만) | ○ | ○ | ○ | ○ |
| Action 요청(채팅·Action 화면) | ○ | ○ | ○ | ○ | ○ |
| Action 승인·거부 | Action 마다 정한 승인 역할만 | 〃 | 〃 | 〃 | 〃(예제는 admin) |
| Action 롤백 | × | × | 승인 역할이면 ○ | × | ○ |
| 알림함 | ○ | ○ | ○ | ○ | ○ |
| 인터뷰 메뉴 | × | ○(내 인터뷰에 답·검토·제출) | ○(검토·초안 게시) | × | × |
| 온톨로지 보기 | ×(메뉴는 보이나 내용 없음) | × | ○ | × | 보기 |
| 온톨로지 고치기·게시 | × | × | ○ | × | × |
| 평가 메뉴 | × | × | ○ | ○ | × |
| 데이터 소스 보기 | ×(메뉴는 보이나 내용 없음) | × | ○ | × | 보기 |
| 데이터 소스·매핑 만들기, 동기화 | × | × | ○ | × | × |
| 편집 충돌 확인·편집 해제 | × | × | ○ | × | ○ |
| 그래프 지금 대사·재구축 | × | × | × | × | ○ |
| 관리 메뉴 | × | × | × | × | ○ |

> **알아 두기** 메뉴가 보여도 내 역할로 쓸 수 없는 화면은 내용이 나오지 않거나 "이 화면을 볼 권한이
> 없습니다"가 나옵니다. 지금 판에서는 일반 사용자에게도 **온톨로지**·**데이터 소스** 메뉴가 보이지만, 눌러도
> 내용이 나오지 않습니다(고장이 아닙니다).

## 29.3 매일 쓰는 사람의 점검표

질문할 때:

- [ ] 대상과 조건을 분명히 적었다(무엇을, 어떤 조건으로, 몇 개/목록/평균).
- [ ] 이름·식별자는 등록된 그대로 적었다(띄어쓰기 포함).
- [ ] 답을 보기 전에 **조회 조건**을 읽었다. 내 조건이 모두 들어 있다.
- [ ] 등급을 확인했다. ②이면 **추정** 문장을 근거 카드로 확인했다.
- [ ] "조회 실패"를 "없다"로 받아들이지 않았다.

데이터 변경을 요청할 때:

- [ ] 미리보기의 **대상**(이름과 식별자)이 맞다.
- [ ] **바뀔 값**의 지금 값 → 실행 후 값이 맞다.
- [ ] **사전 조건**에 ✗ 가 없다.
- [ ] **알림** 받는 사람과 문구를 확인했다. "되돌릴 수 없음"이 있으면 특히 신중하게.
- [ ] 잘못 만들었으면 **요청 거두기** 를 눌렀다.

## 29.4 승인자의 점검표

- [ ] 요청자와 요청 시각을 확인했다.
- [ ] 바뀔 값이 업무 근거(점검 결과 등)와 맞다.
- [ ] 메일·SMS 처럼 되돌릴 수 없는 알림이 있는지 확인했다.
- [ ] 거부할 때는 요청자가 무엇을 고쳐야 할지 **거부 사유**를 적었다.
- [ ] 잘못 실행된 요청은 **롤백** 하고, 받은 사람에게 정정 알림이 간 것을 확인했다.

## 29.5 모델러의 점검표

온톨로지를 게시하기 전:

- [ ] **게시 전 검사**를 모두 통과했다.
- [ ] **버전 비교**로 추가·삭제·변경을 확인했다. 지운 것이 정말 지워도 되는 것이다.
- [ ] 이미 쓰고 있는 타입·속성의 api_name 을 바꾸지 않았다.
- [ ] 새 타입이면 관리자에게 **역할별 읽기 권한** 부여를 요청했다.
- [ ] 게시 직후 채팅으로 대표 질문을 한두 개 물어 보고, 평가를 돌렸다.

데이터 연결 뒤:

- [ ] **접속 시험** 이 성공했다.
- [ ] 매핑에서 pk·제목 속성(별표 `*`)에 원천 열을 골랐다.
- [ ] 첫 동기화가 **성공** 이고 "읽음" 건수가 원천 행 수와 같다.
- [ ] 근거 카드의 **값 출처** 가 새 데이터 소스로 바뀌었다.
- [ ] **편집 충돌** 패널을 주기적으로 확인한다.

## 29.6 관리자의 점검표

- [ ] 새 사람에게는 필요한 역할만 주었다(가장 작은 권한).
- [ ] 퇴사·부서 이동자는 **정지** 했다(지우지 않고 정지 — 기록이 남아야 합니다).
- [ ] 새로 게시된 객체 타입의 **역할별 읽기 권한** 을 정했다.
- [ ] 알림을 메일·SMS 로 받을 사람의 **알림 연락처** 를 넣었다.
- [ ] 문제 신고가 오면 **트레이스** 로 원인을 보고, 그 열람이 감사 로그에 남는다는 점을 알고 있다.
