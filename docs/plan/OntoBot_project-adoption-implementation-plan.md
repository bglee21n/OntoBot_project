# OntoBot 도입 지원 구현 계획 — 초안 (Phase 20~23)

- 상태: **착수(Phase 20)** · 2026-11-02 결정 A1~A11 확정(TRD v1.1 17.17) · 기준 PRD v0.6
- 범위: 사용자 매뉴얼 36장 「도입 현장 양식」(16종)을 앱 안의 **도입 작업 공간**으로 옮기고, 양식의 칸을 기존 기능
  (설계도 draft·골든셋·성공 지표 목표·계정·데이터 그룹·워크숍)에 잇는다. PRD 5.8 v0.6 "인터뷰 전후 도입 절차"의 후속이다.
- 앞선 계획: [MVP](OntoBot_project-implementation-plan.md)(Phase 0~8) · [v1](OntoBot_project-v1-implementation-plan.md)(Phase 9~19).
  Phase 번호는 그대로 이어 붙인다.

## Context

v1 까지의 워크숍은 인터뷰 **안**만 다룬다(6주제 → 요소 후보 → 검토 → draft). 인터뷰 **앞뒤**의 일은 종이 양식(36장)으로만 있다.
목적·범위 합의, 이해관계자, 현장 관찰, AS-IS, 용어 정리, 7요소 설계, 성공 지표 합의, 파일럿 판단, 자산화가 그 일이다.
그래서 양식에 적은 내용을 화면에 다시 손으로 옮겨야 한다. 옮기는 대상은 용어 → 표시 이름·설명·목록 값, 관찰한 질문 →
골든 문항, KPI → 성공 지표 목표, 이해관계자 → 계정·그룹이다. 옮기는 사이에 내용이 빠지거나 바뀐다.

이 계획은 양식을 앱에 저장하고, **사람이 확인하는 "보내기"**로 기존 기능에 넘긴다. 원칙은 v1 과 같다.

- **LLM 이 하는 일을 늘리지 않는다.** 양식 → 제품 연결은 모두 결정론적 변환과 **이름 정확 일치**다(유사도 금지).
  양식 내용은 LLM 에 보내지 않는다(Phase 23 은 측정 조건이 붙은 선택 항목).
- **바로 반영하지 않는다.** 모든 보내기는 기존의 검토 단계를 지난다. 설계도는 draft → 게시 전 검사 → 게시,
  골든은 기대 답 확정, 계정·그룹은 관리자가 적용한다.
- **측정한 프롬프트와 스키마를 건드리지 않는다.** `workshop/topics.py` 6주제, 추출 스키마, 플래너 요약은 Phase 20~22 에서
  바뀌지 않는다. 그래서 `spike_plan`·`spike_workshop` 재측정과 카세트 재녹화가 필요 없다.

## 착수 전 결정 (TRD 17.17 로 반영)

| A8 | 성공 지표 | 시스템 지표 칸은 `evaluation/targets.update` 로 `ops_target` 에 쓴다(있는 지표 키만). 업무 지표는 양식에만 남긴다. **평가 게이트(`gate.yaml`)는 건드리지 않는다** | targets.py 머리말 — 게이트는 설정으로 느슨해지면 안 된다 |
| A9 | 계정·그룹 | 36.6 에서 "계정·그룹 초안"을 만든다. 관리자가 확인하면 `security/admin.create_group`·`create_local_user`·`update_user` 를 부른다. SSO 사용자는 만들지 않고 그룹 `external_id` 만 적는다 | 관리 규칙은 `security/admin.py` 에만(자기 잠금 방지 등) |
| A10 | 자산화 내보내기 | 도메인 팩 모양의 zip 하나: `ontology.yaml`(게시본 내보내기), `golden.yaml`(확정 문항), `adoption/*.json`(양식). **객체 행은 내보내지 않는다.** 합성 시드는 사용자가 올린 CSV 만 넣는다 | 36.15 "실제 데이터는 남기지 않는다". 폐쇄망 밖으로 나갈 수 있는 것만 담는다 |
| A11 | 워크숍과의 관계 | `interview_session.engagement_id`(null 가능)만 더한다. 주제·프롬프트·추출은 그대로 두고, 화면에서 그 도입의 36.9 암묵지 기록을 옆에 띄우는 것만 한다 | 측정한 워크숍 프롬프트를 바꾸지 않는다 |

### Phase 20 — 도입 작업 공간 (저장·양식 편집·인쇄)

- **백엔드**
  - `adoption/` 모듈: `sheets.py`(16종 스키마, 순수)·`store.py`(도입·양식 CRUD, revision 증가, 감사)·`progress.py`(단계별
    "다음 단계에 넘길 것"이 채워졌는지 판정, 순수).
  - 모델·마이그레이션: `engagement`·`engagement_sheet`·`engagement_member`. 감사 이벤트는 `adoption.*`.
  - API(`api/adoption.py`, 검증·위임만): 목록·만들기·구성원, `GET /adoption/sheet-kinds`(JSON Schema),
    양식 읽기·저장(낙관적 잠금 `revision`). `rbac.engagement_access` 를 더한다.
- **프론트**: `features/adoption/` 의 세 화면.
  - 도입 목록
  - 도입 한 건: 다섯 단계 탭과 진행 표시
  - 범용 양식 편집기: 스키마로 표·체크·선택 칸을 그린다
  - 인쇄 보기는 CSS print 로 만든다. 빈 칸 높이 규칙은 매뉴얼 빌드와 같다.
  - 메뉴 "도입"은 modeler·admin 과 구성원에게만 보인다.
- **테스트**
  - 단위: 스키마가 36장의 칸과 맞는지, progress 판정, rbac.
  - 통합: 구성원 아닌 사람 404(없는 도입과 같은 말 — TRD 17.17), revision 충돌 409, 감사 payload 에 양식 값이 없음.
  - 계약: OpenAPI.
- **완료 기준**: 샘플 도메인으로 도입 한 건을 만들어 16종을 저장·재열기·인쇄한다. 구성원이 아닌 계정은 보지 못한다.
- **진행 기록(2026-11-02, 완료)**: 마이그레이션 0021, `adoption/sheets.py`(16종 — 36.16 순서표의 기간·누가도 입력 열),
  `progress.py`, `store.py`, `api/adoption.py`, 화면 `features/adoption/`(목록·도입 한 건·범용 편집기·CSS print).
  계획과 다른 점: 구성원이 아니면 403 이 아니라 404(워크숍 세션과 같은 말), 도입 정보 고치기(`PATCH`)를 더했다.
  검증: 단위(선언 ↔ 매뉴얼 36장 표 머리글·고정 행 대조 포함)·통합(권한·마지막 owner·판 충돌·감사 payload 에 양식 값 없음)·
  계약, 브라우저(격리 테스트 DB 로 만들기 → 저장 → 판 충돌 → 다시 불러오기 → viewer 읽기 전용·메뉴). 매뉴얼 36장 화면
  사진과 Word·PDF 재생성은 하지 않았다(본문에 앱 사용 안내만).

### Phase 21 — 양식 → 제품 보내기

모든 보내기는 결정 A5 의 미리보기 → 적용을 따른다. 변환 규칙은 `adoption/bridges.py`(순수, 단위 테스트)에 모은다.

| 보내기 | 출발 양식 | 받는 곳(기존 함수) | 규칙 |
| --- | --- | --- | --- |
| 21a 용어 → 설계도 | 36.11 용어집, 36.12 7요소 | draft: `versioning.create_draft`·`add_object_type`·`add_property`·`replace_property`·`add_link_type` | `api_name` 정확 일치면 표시 이름·설명·목록 값만 갱신, 없으면 추가 후보. 자료형이 바뀌는 갱신은 미리보기에서 막고 이유를 보인다. "흔들리는 말" 표의 합의 정의 → 목록 값과 설명 |
| 21b 질문 → 골든 후보 | 36.7 관찰 기록, 36.9 암묵지, 36.4 성과 질문 | `golden_item(source=adoption)` | 질문 문장 그대로. 같은 문장(NFC·공백 정규화 뒤 정확 일치)이 이미 있으면 건너뛴다. 기대 답은 평가 화면에서 확정 |
| 21c KPI → 성공 지표 목표 | 36.14 시스템 지표 칸 | `evaluation/targets.update` | 아는 지표 키만, 단위 변환은 스키마에서. 게이트 미변경 |
| 21d 이해관계자 → 계정·그룹 초안 | 36.6 | `security/admin.create_group`·`create_local_user`·`update_user` | 그룹 이름·사용자 아이디 정확 일치로 기존 것과 맞춘다. 임시 비밀번호는 화면에 한 번만 보인다. 관리자 역할 필요 |
| 21e 인터뷰 연결 | 36.9 | `interview_session.engagement_id` | 세션 화면 옆 패널에 그 도입의 36.9 기록(읽기 전용) |

- 36.8 AS-IS 의 "설계도 후보" 열은 21a 의 입력으로 함께 쓴다(대상 → 객체 타입 후보, 바꾸는 일 → Action 후보 메모).
  Action 정의 자체는 만들지 않고 Action 편집기(17장)로 링크만 건다. 사전 조건·알림은 사람이 정의해야 한다.
- **테스트**
  - 단위: bridges 의 변환·충돌 판정. 같은 입력을 두 번 보내면 차이가 0 인지.
  - 통합: 21a draft 생성 → 게시 전 검사 통과, 21b 중복 건너뛰기, 21c 게이트 파일 불변, 21d 자기 잠금 방지가 그대로인지.
- **완료 기준**: 샘플 도입에서 용어집 → draft → 게시 → 그 용어로 한 질문이 ①. 관찰 질문 3개 → 골든 확정 → 평가에 나타남.

### Phase 22 — 파일럿 판단·자산화

- **36.14 판단 패널**: 마지막 실제 모델 평가 실행(재생 제외)의 게이트 결과·불변식, `targets.load` 의 목표 대비 지금 값,
  업무 지표(양식)를 한 화면에 모은다.
  - 판단(Go / 보완 뒤 Go / No-Go)과 사유는 사람이 고르고 감사로 남긴다.
  - **불변식 위반이 있으면 Go 를 고를 수 없다**(서버 검증).
- **36.15 내보내기**(결정 A10): `adoption/export.py` 가 zip 을 만든다.
  - 설계도는 `ontology/importer.dump` 형식을 쓰고, 골든은 `golden.yaml` 형식으로 담는다.
  - 업로드한 합성 CSV 는 원천 매핑의 열 이름과 맞는지만 검사한다.
  - 내보내기는 감사 이벤트로 남긴다.
- **테스트**: 통합에서 불변식 위반 eval_run 이 있으면 Go 가 422 인지, zip 에 `object` 행이 없는지, 재가져오기
  (zip 을 `domain-packs/<이름>/` 에 풀고 `seed_domain_pack.py --pack <이름>`)로 골든 기대값이 다시 계산되는지 확인한다.
- **완료 기준**: 샘플 도입 하나를 끝까지 돌린다. 판단 기록 → zip → 새 평가 DB 에 시드 → `eval-replay` 가 아닌 실제 게이트 통과.

### Phase 23 (선택) — 용어집 동의어를 플래너에 싣기

- 36.11 의 "같은 뜻의 다른 말"을 정의 문서의 속성·타입 `aliases` 로 옮겨 플래너 요약에 싣는다.
  **조건**: 실제 도입에서 동의어 때문에 틀린 질문이 골든으로 확인되었을 때만 시작한다.
- 위험이 크다.
  - 정의 문서·`content_hash`·플래너 프롬프트·카세트 키가 모두 바뀐다.
  - `aliases` 가 비었을 때는 정의에서 빠지게 한다(`drop_default_flags` 와 같은 방법). 그래야 기존 게시본 해시가 그대로다.
- 필요한 측정: `spike_plan.py --models gemma4:e4b` 재측정 → ADR-0004 기록 → `eval-record` → 카세트 커밋.
  동의어 대조는 정확 일치뿐이고, 유사도 확장은 하지 않는다.

## 문서

- **TRD:** 17.17(결정 A1~A11)과 Phase 마다 절을 하나씩 둔다. 개정 이력에 남긴다.
- **PRD 5.8:** "인터뷰 전후 도입 절차"를 문서에서 기능으로 바꾸고, 8절 로드맵에 넣는다.

  - 양식 → 제품 보내기는 미리보기 → 적용, 이름 정확 일치.
